### 1.1 盘点发现的问题

第 7 项改变审计输出，归入 M1；其余各项不改变 DSL 语义，归入 M0。

1. **仓库只在本机。** 没有配置 git 远端，也没有 CI。
2. **文档已经漂移。**
   - README 仍写 Compare POST、Explain、编辑与 SSE“当前返回 501”；项目结构表缺 `mantra-excel` 和 `explain` 命令。
   - 架构 §3 仍称“编辑、Explain 和 SSE 属于后续工作包”。
   - RFC 0001 摘要仍称 WP1 的三项修复“尚未合入主分支”。
   - DSL 参考 §1.4 缺 `alloc/waterfall`、`table/band`、`fin/pmt`。
   - 契约 §6 的外层示例仍写旧内核 `be7648b5`。
3. **结果视图未完全收口（WP2 遗留）。** `mantra-render`、`mantra-excel`、`mantra-workbench` 和 `mantra-cli` 仍从 `core.engine` 导入 `CalculationResult`、`Coord`、`NodeTrace`、`TraceRef`、`ExplainTrace`、`FormulaAuthoring`、`MantraLibrary` 等类型。作为库发布前，公开类型须移出 `engine` 包。
4. **测试分布不均。**
   - `mantra-render` 约 2,200 行主代码，只有 12 个测试。
   - `mantra-excel` 有 4 个测试；示例模块的逐值比对只覆盖 ESt 与 IAS 36 IE8 两个案例。
   - `mantra-cli` 只有 2 个测试，都针对 `diff` 的修订计算。
5. **代码形态不利于审阅。**
   - `InputsPage.tsx`、`ReadOnlyPages.tsx`、`App.tsx` 中有 1,100–1,700 字符的单行。
   - `ExcelWorkbookBuilder.kt`（1,187 行）、`WorkspaceCatalog.kt`（921 行）和 `WorkbenchServer.kt`（666 行）各自承担多项职责。
   - 仓库没有格式化或静态检查工具。
6. **边界只靠约定。** 契约 §12 要求 CI 检查前端源码不含方案标识符，目前未见实现；引擎模块也没有同类检查。
7. **审计附录与 Explain 不同源。** 纸面、HTML 与 XLSX 的 Rechenweg 仍由 `FormulaExplainer` 代入根值，工作台 Explain 已使用内核的逐步 trace。RFC 0001-F 的 Mantra 侧迁移尚未完成。
8. **开源准备不足。**
   - 仓库没有许可证、贡献指南和安全说明；公开文档以中文为主。
   - 一个验收样例的目录与方案 id 带第三方商标（`sap-co-product-cost`、`sap.co/product-cost`）。
   - Normein 已具备这些：Apache-2.0、`CONTRIBUTING.md`、`SECURITY.md`、`SUPPORT.md`、`THIRD_PARTY_NOTICES.md`，以及以 `com.xqiou` 发布到 Maven Central 的脚本。Mantra 可以沿用。

## 2. 定位、愿景与约束

**定位（R1）。** Mantra 是开源、通用的计算方案库，关注跨领域共通的底层逻辑和核心能力：

- 计算原语与表格原语；
- 精确求值、追溯与诊断；
- 一致的多种输出；
- 稳定的公开接口。

**展示应用（R3）。** 仓库是一个 monorepo：根目录是引擎库，`apps/` 中是完整的领域展示应用。展示应用：

- 证明通用性，示范从方案到底稿、工作簿和工作台的完整用法；
- 只依赖公开 API；
- 不作为库制品发布，也不是生产用的税务或会计软件。

**愿景。** 方案作者用 DSL 定义方案，使用者以案例、参数和版式使用方案。每个数都精确、可追溯、可复算，以 Staffel、矩阵、底稿和 XLSX 呈现，经得起审阅（Prüfpfad、Fußung）。

**通用性的检验标准。** 加入新领域时需要新增的计算原语越来越少，多数需求靠组合现有原语满足。

### 2.1 范围

| 部分 | 内容 | 发布方式 |
| --- | --- | --- |
| 引擎库 | 计算原语、表格与呈现原语、预设；求值、维度、期间、条件、舍入、追溯与诊断；HTML、Text、XLSX、PDF 输出与 JSON 契约；格式层的数据适配器（CSV、JSON、XLSX） | Maven Central 制品 |
| 工具 | CLI、参考工作台、编辑器支持（LSP） | 随引擎发布 |
| 展示应用（`apps/`） | 领域方案、参数集、版式、导入模板、案例、核对脚本和说明 | 随仓库提供，不发布为库制品 |
| 范围外 | 申报与传输（如 ELSTER）、记账、ERP 集成；多用户部署、权限、审阅签核等业务流程；领域专用界面；生产级的法规完整性与时效保证 | — |

### 2.2 不变约束

| # | 约束 | 出处 |
| --- | --- | --- |
| C1 | 引擎、工作台和前端不含业务逻辑；领域内容只在 `apps/` 的方案中 | CLAUDE.md、R3 |
| C2 | 新计算原语至少由两个领域论证，并满足“原语上提规则” | CLAUDE.md、职责契约 |
| C3 | 同一口径：核心求值、纸面、XLSX、Explain 与工作台对同一个值给出同一结果；XLSX 不能静默退化成固定值 | 职责契约 |
| C4 | 文档是唯一事实来源：链接、版本等新功能都必须落成工作区文档 | 契约 W1 |
| C5 | 数值精确，舍入显式 | CLAUDE.md |
| C6 | 不修改 Normein；内核需求写成 RFC，经契约测试接入 | CLAUDE.md、RFC 0001 |

### 2.3 原语完成定义

每个新的计算或呈现原语在合入前满足：

1. 语义写入架构文档，包括维度、条件、空值、舍入和诊断代码；
2. `mantra-core` 或 `mantra-render` 中有单元测试；守恒类原语另有性质测试，例如分摊合计守恒；
3. 至少两个领域有验收案例，数值有独立来源；
4. XLSX 可重算，或在导出报告中显式列为回退；
5. trace 与 Explain 能解释该值；
6. 工作台经契约呈现，前端没有特例；
7. `mantra catalog` 与 DSL 参考同步。

### 2.4 展示应用完整度标准

`apps/` 中的应用在列为“完整”之前满足：

1. 只依赖库模块的公开 API，由 Gradle 依赖和架构测试共同约束；
2. 方案包齐全：方案与片段、参数集、版式；数据驱动的应用另带导入模板与样例数据；
3. 案例覆盖主场景和边界情形，例如阈值两侧、不适用的分支、择优的不同结果；
4. 预期值来自独立来源：公开示例或复算脚本（C7）；
5. CI 渲染 HTML、Text 与 XLSX，XLSX 通过逐值比对；
6. 工作台不需要任何特例就能打开、浏览、编辑和导出；
7. 英文 README（R8）写明演示的原语、核对来源、运行方式和简化之处，并声明仅作展示、不构成税务或会计建议；
8. 方案中的简化以注释标出，如现有 ESt 方案的 `;; Vereinfachung`。

**为什么 monorepo 放在 M0**

- M1–M3 会陆续新增 IAS 12、资产变动表、IFRS 16 和 GewSt 等应用；先定结构，这些应用一开始就建在 `apps/` 中，免得以后再搬一次。
- 公开 API 收口与边界检查都需要明确“应用”与“库”的分界，迁移后这条分界由模块依赖直接表达。

**为什么校验排在期间之前**

- M1 只回应现有三个应用已经暴露的需求，风险小、见效快。
- M2 的资产变动表和租赁表都要核对期末余额，需要 M1 的对账原语。
- 审计呈现是 Mantra 的核心价值；让 Rechenweg 与 Explain 同源，不宜继续推后。

## 4. 里程碑详情

### M0 巩固、开源准备与 monorepo（v0.1.x）

**目标**：不改 DSL 语义，把 v0.1 的交付速度转成可持续、可公开的工程基线，并建立 monorepo 结构。

**建议顺序**：远端与 CI → monorepo 迁移 → 公开 API 收口与边界检查 → 其余各项并行。

- **远端与 CI**
  - 建立远端并推送。维护者已于 2026-10-03 确认使用公开仓库，覆盖 R10 原定的公开时点；其余发布条件不变。
  - Normein 的锁定提交已在其远端 `origin/main` 上。`bootstrap-normein.sh` 默认使用 SSH 地址；CI 使用专用只读 deploy key 检出锁定提交，凭据不进入构建缓存或产物。
  - CI 任务：先安装前端依赖，再运行 `./gradlew --no-daemon check`；在 `workbench-ui` 中执行 `npm ci`、`npm test`、`npm run build` 和 `npm run test:e2e`（无头浏览器）。
- **Monorepo（R3）**
  - `examples/` 迁为 `apps/<应用>`，每个应用是一个 Gradle 子项目（如 `:apps:de-est`），只依赖库模块；库模块保持在根目录。
  - SAP CO 风格样例改用中性的目录名与方案 id（如 `apps/cost-accounting`），说明中保留“SAP CO 风格”的描述。
  - 工作台 golden 与 `mantra fixtures` 改从 `apps/` 生成；同步修改 CLAUDE.md、README 与架构文档中 `examples/` 的表述。
  - 现有三个应用按 §2.4 补齐。
- **公开 API 收口**
  - 架构测试：`mantra-core` 以外不导入 `core.engine`。
  - 公开类型移到 `core.view` 或新的 `core.api`，并补 KDoc；`mantra catalog` 经公开 API 读取函数目录。
  - 这同时界定了库的公开面：此后只有这些包受 C8 的版本约束，`apps/` 也只能使用这些包。
- **边界自动检查**：从 `apps/` 的方案提取方案与节点标识符，扫描 `workbench-ui/src` 和引擎各模块的主代码，出现即失败。这落实契约 §12，并把检查扩展到 CLAUDE.md 规定的引擎边界。
- **质量门**
  - Kotlin 与 TypeScript 的格式化和静态检查，例如 Spotless 配合 ktlint 或 detekt，Prettier 配合 ESLint。
  - 重排前端超长行；按职责拆分 `ExcelWorkbookBuilder`、`WorkspaceCatalog`、`WorkbenchServer`，不改行为。
- **测试补强**
  - 全部案例的 HTML 与 Text golden；
  - 版式选择器、预设和行号的 `mantra-render` 单元测试；
  - 七个 CLI 命令（`run`、`check`、`catalog`、`fixtures`、`diff`、`explain`、`serve`）的冒烟测试；
  - XLSX 逐值比对覆盖全部案例，包括 SAP CO 与 IAS 36 自定义加权。
- **文档同步**：修正 §1.1 第 2 项；增加一个测试，核对 `mantra catalog` 的函数目录与 DSL 参考 §1.4 一致。
- **性能基线**（T2）：编写合成方案生成器，按行数、成员数和表格行数伸缩，记录 plan、calculate、explain、paper 和 xlsx 的耗时与内存。
- **开源准备**
  - 沿用 Normein 的配置：Apache-2.0 许可证（R9）、`CONTRIBUTING.md`、`SECURITY.md`、`SUPPORT.md`；`THIRD_PARTY_NOTICES.md` 列出 POI、Jackson、React、CodeMirror 等依赖。
  - README 与入门文档用英文（R8）。
  - 公开前核查引用 IFRS 示例数据的方式，因为 IFRS 文本受版权保护。

**退出条件**

- 从干净检出运行 CI 全绿；
- 三个现有应用迁入 `apps/`，满足 §2.4；
- `mantra-core` 以外没有 `engine` 导入；
- 目录一致性测试通过；
- 性能基线写入 §5 的 T2；
- 许可证与社区文件就位，仓库可以公开。

**完成记录（2026-10-04）**：全部退出条件通过。三个应用、公开 API 边界、质量门、职责拆分、

### M1 校验、对账与审计呈现（v0.2）

**目标**：业务校验与对账成为一等公民；纸面上的 Rechenweg 与 Explain 同源。

**引擎**（形式为草拟，语法在工作包设计时确定）

| 能力 | 草拟形式 | 领域论证 |
| --- | --- | --- |
| 声明式校验 | `(check id "标题" <布尔表达式> {:severity :error :per …})`，`:severity` 取 `:error` 或 `:warning`。在节点维度上求值，不改变数值；失败时产生带地址的诊断（拟 `MANTRA-CHECK-FAILED`） | SAP CO：成本池非零时分配基数之和须为正；ESt：单独申报却填了 Person B 的数据；IAS 36：CGU 账面价值不得为负 |
| 条件必填与基数 | 输入的 `:required-when <表达式>`；表格的最少行数 | SAP CO：直接费用必须填工单；IAS 36 与 SAP CO：至少一个 CGU 或工单 |
| 对账 | 校验的特例：两侧取值与差额进入纸面，差额超出容差即失败 | SAP CO：来源 → 工单 → 产品的对账（现为普通行）；IAS 12：税率调节表；M2 的资产变动表 |
| 比率度量 | `:aggregate {:ratio [分子 分母]}`：横向合计 = Σ分子 ÷ Σ分母，舍入显式 | SAP CO：产品加权单位成本；IAS 12：实际税率；ESt：平均税率 |

职责契约第 1 项（`formula-slot` 的字段级与函数级许可）等到第二个领域使用公式槽时再做（C2）。

**表现层**

- Rechenweg 改用内核逐步 trace（RFC 0001-F 的 Mantra 侧迁移）：HTML、Text 与 XLSX 的审计附录与 Explain 同源，golden 相应更新；
- 校验与对账结果进入 `:status` 列（拟新增 ✗），XLSX 生成可重算的校验公式；
- 表格输入的诊断定位到单元格（架构 §9 记录的限制）。

**工作台**：校验结果进入诊断页和对应的板块单元格。契约先增加诊断类别与对账字段，再改代码。

**展示应用**

- 三个现有应用改用校验与对账原语。
- 新增 `apps/ifrs-income-taxes`：IAS 12 税率调节表（单期）。按法定税率计算的预期税费，加调节项，等于实际税费，并给出实际税率；数值来自公开示例或独立复算脚本。

**退出条件**：新原语满足完成定义；SAP CO 的对账行改由对账原语表达；四个应用通过验收。

**不做**：校验失败不阻止计算和保存（R6）。

### M2 连续期间（v0.3）

**目标**：按 R2 采用类似 SAP 连续期间的模型——期间连续，每期都有期末，下一期从上一期的期末开始；同时把多个维度排成底稿。

**语义（R2）**

- **连续期间维度**：成员按顺序排列，中间没有缺口，除首期外每期有唯一的上一期。成员可以静态列出，也可以由起始日期、期间长度（月、季、年）和期数生成，以支持非日历财年。
- **每期都有期末**：余额类节点（存量）在每个期间都有期末值。下一期的期初等于上一期的期末，即逐期结转；首期期初来自输入，或来自前一案例（M3）。
- **上一期引用**：引用同一节点在上一期的值，首期显式给出缺省值，草拟为 `(prev closing opening-balance)`。规划器在成员层面排序：沿期间严格向前的引用不构成环；其他自引用仍报 `MANTRA-CYCLE`，路径带期间。
- **逐期求值**：按期间顺序逐期求值，每期的期末都可寻址、可 Explain、可导出。整列用 `reduce` 一次算出全部期间的做法因此不采用。
- **存量与流量**：跨期汇总时，存量取末期期末（期初取首期期初），流量求和。这扩展 M1 的度量语义（`:aggregate`）。
- **期间层级**：月 → 季 → 年等层级复用 `:parent` 与 `dim/rollup`，并按存量与流量规则汇总。
- **时间方向的 Staffel**：期初加变动，以 `total` 得到期末，复用现有 section 与 total 语义；M1 的对账原语核对期末与外部余额。
- **期间计算**：Normein 已有 `date/days-between`、`date/months-between`、`date/plus-months`、`date/end-of-month` 等函数。计息天数惯例（如 act/365、30/360）若有两个领域需要，作为 `fin/*` 函数加入 `mantra.calc`。

**表现层**

- **二维矩阵**：行为项目 × 一个维度的成员（分组并带小计），列为另一个维度的成员，例如资产 × 年度。架构 §9 的“只支持一个成员维度作为列”的限制在此解除。
- **转置**：成员为行、项目为列。这是资产变动表、递延税变动表和准备金变动表的通常形态。
- **XLSX**：上一期引用译为相邻单元格的相对引用；期间层级的汇总列按存量与流量规则生成公式；`date/*` 译为 `EDATE`、`EOMONTH` 等函数。

**工作台**：呈现二维板块；Explain 把上一期引用显示为来自上一期的期末。地址已支持多维坐标，不需要改格式。

**展示应用**

- **`apps/ifrs-impairment`**：由现金流计算使用价值（CGU × 年度），补齐架构 §8 的 🟡 项；同时补 IAS 36.105 的带上限分摊案例（`alloc/capped`）。
- **新增 `apps/fixed-assets`**：资产 × 年度的直线折旧逐期结转，对应 IAS 16.73(e) 的账面价值调节和 HGB § 284 Abs. 3 的资产变动表；用独立复算脚本核对。
- **新增 `apps/ifrs-leases`**：IFRS 16 租赁负债按实际利率逐期结转，使用权资产折旧；用公开示例或独立复算核对。

**退出条件**

- 新原语满足完成定义；
- 存量与流量规则在纸面、XLSX 与 Explain 中一致；
- 两个新应用满足 §2.4；
- 同平台复测 M0/M1 场景，并测量 200 项资产 × 10 年；报告耗时、内存和退化原因，以实测数据明确预算。M0 只有测量基线，尚未设硬时间门槛。

### M3 跨案例延续与有界迭代（v0.4）

**目标**：上一年的结果、另一个方案的结果，都作为可追溯的输入进入计算，不再手工抄数；支持受控的循环计算。

**引擎**

- **案例链接**（暂名 `(links …)`）：案例声明被链接案例的路径、期望的方案 id 与版本，以及“对方节点及坐标 → 本方输入”的映射。它有两种用途：
  1. **跨案例延续**：前一案例末期的期末成为本案例首期的期初，相当于 SAP 的年度余额结转，与 M2 的逐期结转是同一条规则。前一案例变化时，本案例的修订号随之变化，相当于自动重做结转。
  2. **跨方案传值**：一个方案的结果作为另一个方案的输入，例如 GewSt 的 Messbetrag 进入 ESt 的 § 35 EStG。

  约束：
  - 被链接案例按其自身绑定独立计算，本方修订号包含被链接案例的全部参与文件；
  - 跨案例的环路报错，链接深度设上限；
  - 输入来源记为 `link:<案例>#<节点>`，与数据来源的 `source:` 并列。
- **有界迭代**：按 RFC 0001 契约 G 实现 `calc/converge`：最多 1,000 次迭代，未收敛报 `MANTRA-CALC-NOT-CONVERGED`，受内核预算约束；`mantra.calc` 升到 2。
- **运行级预算**：内核只有单次求值的预算（RFC 0001 资源上限表）。Mantra 为整次运行设上限（成员组合 × 行 × 链接案例），并让 `mantra.calc` 的函数按实际工作量计费。

**表现层与工作台**

- 纸面注明链接值的来源案例与修订；XLSX 把链接值写成带来源批注的输入单元格，不生成跨工作簿公式。
- 工作台显示案例链；Explain 可跨案例展开，地址因此增加案例字段（先改契约）；被链接案例变化时，经 SSE 提示下游案例。

**展示应用**

- **`apps/de-est`**：2024 → 2025 的 § 10d EStG 亏损结转。现 ESt 方案的 `verlustvortrag` 是手工输入，改为链接。
- **新增 `apps/de-gewst`**：单一企业的 GewSt（Hinzurechnungen、Freibetrag、Messbetrag、Hebesatz）；其 Messbetrag 链接到 ESt 方案已有的 `gewst-messbetrag` 输入。
- **循环计算**：例如以扣除奖金后的利润为基数计算奖金，放在合适的应用中，用闭式解独立核对。

**退出条件**：新原语满足完成定义；CLI 与工作台都能解析链接；跨案例环路、修订传递和链接深度有测试；`apps/de-gewst` 满足 §2.4。

### M4 嵌入与规模（v0.5）

**目标**：作为库被其他程序嵌入时，接口稳定、可批量、可升级。

- **嵌入 API**
  - 宿主程序以类型化数据直接提供输入和参数，不必先生成案例文本；
  - 结果只经只读视图（M0 收口的公开类型）读取；
  - 自定义输出端只依赖视图。
- **编译一次、多次求值**：同一方案、参数集和扩展的编译结果在多个案例间复用；提供批量计算 API；无审计时走 VALUE_ONLY（T2）。
- **方案版本**（职责契约第 6 项、契约 D5）
  - 方案声明语义版本，案例记录所用版本；
  - 不同版本并存，或经显式、可审阅的迁移升级（R7）；迁移复用契约 §7 的编辑操作。
- **方案包**：方案、片段、参数集、版式和导入模板可以打包，从目录或 classpath 加载（`ClasspathSources` 已有）；清单声明包 id、版本和兼容的引擎版本范围。
- **参数集有效期**：参数集声明适用期间与出处；按键选择的参数表在求值前由宿主解析，不把整张表构造成内核值（见 §5 的大表策略）。
- **API 兼容检查**：公开 API 由二进制兼容检查守护（例如 Kotlin binary-compatibility-validator），进入 CI。

**展示应用**

- 每个应用都以方案包的形式加载；
- 一个应用附带只经公开 API 的嵌入示例程序，例如用 `apps/ifrs-leases` 批量计算租赁组合；
- `apps/de-est` 演示一次方案版本迁移（例如 `2025.1` → `2025.2`）。

**退出条件**：批量基准（例如同一方案 10,000 个案例）达到 T2 预算；上述展示通过；API 兼容检查进入 CI。

### M5 开发者体验（v0.6）

**目标**：降低方案作者和集成者的使用门槛。

- **LSP**
  - `mantra lsp` 语言服务器为 `.mantra` 文件提供诊断、宿主形式与嵌入公式的补全、带目录说明的悬停、跳转与查找引用、节点重命名。
  - 复用 `DslAuthoringService`、`hostPosition` 与 `mantra catalog`，这是 RFC 0001-H 划给领域层的工作。
  - VS Code 与 IntelliJ 插件只做薄封装。
- **文档站点**：英文（R8）的教程、DSL 参考、函数目录、诊断代码目录和 API 文档；目录类内容由代码生成。
- **展示库**：文档站点为每个应用设一页，附 CI 渲染的底稿与工作簿，并链接到应用的 README；`mantra serve apps` 可以在工作台中打开全部应用。
- **PDF 与打印**：可打印的底稿，含页眉页脚、分页和审计附录；作为呈现原语进入 `mantra-render` 测试。
- **诊断本地化**：诊断按代码本地化（契约 D2），依赖诊断代码目录。
- **参考工作台**：保持通用的阅读器和结构化编辑器，跟进二维板块、校验、链接与版本的呈现；无障碍与深色主题（颜色已全部令牌化）。不加入审阅签核等业务流程（R1）。

**退出条件**：新用户按教程能从零写出、运行并导出一个方案；展示库覆盖全部应用；端到端流程覆盖新能力；契约不兼容时提升主版本（W5）。

### M6 v1.0 稳定版

**退出条件**

- 语言规范 v1：宿主形式、维度、期间、条件、舍入与诊断代码；
- 一致性测试套件：与实现分离、按规范条目组织，可用于回归测试，也可供其他实现验证；
- 兼容策略成文：DSL、Kotlin API、JSON 契约与 `mantra.calc` 库各自的版本规则和弃用流程（C8），以及与 Normein 版本的对应关系；
- 至少五个应用满足 §2.4；通用性目标：最近加入的两个应用没有要求新的计算原语；
- 性能预算达标（T2），安全审查通过（T5）；
- 文档站点完整。

### v1.0 之后（方向）

- **非 JVM 集成**：其他语言的程序经 CLI 或本机服务的 JSON 契约使用引擎；确有需求时再考虑语言绑定。
- **社区方案**：第三方的领域方案以方案包发布在本库之外，只依赖公开 API；`apps/` 仍只收展示应用。
- **更多领域**：见 §6。

## 5. 横向主线

| 主线 | 持续要求 | 各里程碑重点 |
| --- | --- | --- |
| T1 工程与质量 | CI 全绿；每个模块有测试下限；单文件与单行长度受检查 | M0 建立；M2 起 XLSX 覆盖随新原语扩展，包括增删表格行的动态范围与更多高阶函数；M4 增加 API 兼容检查 |
| T2 性能与规模 | 每个里程碑与基线对比，退化须说明原因 | M0 [合成性能基线](performance-baseline.md)；M2 无审计的计算改走 Normein 执行计划与会话（VALUE_ONLY），只有审计与 Explain 使用 FULL trace；M2 起编辑后按依赖图增量重算；M3 运行级预算；M4 编译复用、批量计算与大表策略 |
| T3 Normein 协同（R4） | 两个项目同步推进：每个里程碑开工时把内核需求写入 RFC（从 0002 起编号），Normein 并行实现并发布；Mantra 在里程碑内经契约测试接入已发布的提交，不修改内核（C6） | M0 确定 [`normein-dsl` 制品发布方式](normein-publication.md)；M1 起每个里程碑配一个 Normein 版本；C 项整数策略随下一个 Normein 版本确定；对外发布时两边制品同时发布 |
| T4 文档与开发者体验 | 语义以架构文档为准；目录类文档由代码生成，或由测试核对；公开文档用英文（R8） | M0 目录一致性测试与英文 README；M1 诊断代码目录；M5 文档站点与展示库；M6 语言规范 v1 |
| T5 安全与合规 | 只监听回环地址；文件访问限于工作区；案例数据保持虚构 | M0 建立依赖更新机制（POI、Jackson 等）；M3 校验链接路径；M4 校验方案包来源；1.0 前审查导入解析（超大 CSV、XLSX 解压炸弹） |
| T6 发布与社区 | 语义版本；每个版本附变更记录；弃用先标记、再移除；`apps/` 不发布为库制品 | M0 社区文件；仓库已按维护者确认提前公开；首个制品随 `normein-dsl` 发布（最早在 M1 之后）；M6 发布 1.0 |

**大表策略（T2）。** 内核值上限是硬约束：被公式引用的一个值最多 10,000 项，三列表格约 1,428 行；集合最多 5,000 项。费用流水、按地区的参数表、资产 × 期间都会很快触及。可选做法：

1. 在方案中显式、可追溯地预聚合；
2. 宿主在求值前按键解析参数；
3. 向 Normein 提出 RFC（T3）。

数据适配器不得在读取阶段暗中计算业务结果（职责契约）。

## 7. 决策

全部路线级问题已于 2026-10-03 确定。语法等设计问题在各里程碑的工作包中决定；新的路线级问题出现时，在本节追加。

| # | 问题 | 决定 | 对路线图的影响 |
| --- | --- | --- | --- |
| R1 | 定位 | 开源库，保持通用，关注底层共通的逻辑与核心能力 | §2 的定位与范围；M4 为嵌入与规模，M5 为开发者体验；审阅签核与部署形态不在范围内 |
| R2 | 上一期 | 采用类似 SAP 连续期间的模型：期间连续，每期都有期末，下一期从上一期期末开始 | M2 的语义；M3 的跨案例延续沿用同一规则 |
| R3 | 领域样例的去向 | 保留 monorepo：`apps/` 中是完整的展示应用，只依赖公开 API，不发布为库制品 | §2.4 完整度标准；迁移放在 M0；每个里程碑的新领域直接建为应用 |
| R4 | Normein | Normein 同步推进 | T3 按里程碑协同发布；对外发布时同时发布 `normein-dsl` 制品 |
| R5 | 部署形态 | 多用户部署不在本库范围；工作台保持本机参考工具 | §2.1；M5 |
| R6 | 校验失败的效力 | 只报告，不阻止计算和保存；需要阻止时，由使用者的程序依据诊断决定 | M1 |
| R7 | 方案升级后的旧案例 | 旧版本并存，迁移显式且可审阅 | M4 |
| R8 | 公开文档的语言 | README、教程、DSL 参考、API 文档和应用说明用英文；架构、契约等设计文档暂留中文，逐步翻译 | M0、M5、T4 |
| R9 | 许可证 | Apache-2.0，与 Normein、POI、Jackson 一致，并含专利授权条款 | M0 |

## 8. 风险

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| 本机单点 | 没有远端与 CI | M0 第一项 |
| 核对跟不上实现 | 现有 73 个提交都在 2026-09-27；寻找独立核对来源和审阅比编码慢 | 每个里程碑先锁定核对来源和复算脚本；工作包 §5 的审阅清单不省略 |
| 口径分叉 | 新原语只在核心实现，XLSX、Explain 或工作台落后 | 原语完成定义；XLSX 逐值比对覆盖全部案例 |
| 业务逻辑渗入引擎 | 在 monorepo 中图方便，把应用逻辑写进引擎，或让应用调用内部类型 | 应用只依赖公开 API；M0 的边界自动检查；原语上提规则 |
| 展示应用被当作生产软件 | 使用者把展示方案直接用于申报或审计 | README 的声明；简化之处在方案中标注；不承诺法规时效（§2.1） |
| 展示完整度拖慢引擎 | 补案例、说明和核对脚本占用里程碑的大部分精力 | 完整度标准只要求 §2.4 所列内容；每个里程碑只新增一到两个应用 |
| 内核上限 | 大表与多维计算触及值上限和求值预算 | T2 的基线与大表策略；必要时提 RFC |
| 两个项目的版本耦合 | Mantra 的发布等待 Normein 的发布 | T3 的协同节奏；只依赖已发布的 Normein 提交；契约测试提前发现行为变化 |
| 公开 API 过早固化 | 0.x 使用者依赖了内部类型 | M0 只公开 `view`/`api` 包；0.x 明示不稳定；M4 起做兼容检查 |
| 文档漂移 | 已经出现（§1.1 第 2 项） | 目录一致性测试；每个工作包同步文档（工作包 §1） |
| 第三方依赖 | POI、Jackson 等需要安全更新 | T5 的依赖更新机制 |

## 9. 维护本路线图

- **里程碑开工**：先锁定独立核对来源，再评估内核需求（T3），然后按工作包格式（必读顺序、任务单模板、审阅清单）拆分；工作包写在 `docs/milestones/m<n>-work-packages.md`。
- **里程碑完成**：更新 §1 的现状和 §3 的状态，发布对应的 0.x 版本，在变更记录中写明偏差与推迟项。
- **语义与契约**：语义变化先改架构文档，工作台接口变化先改 `contract.md`（CLAUDE.md）。已定决策的变化也记入变更记录。
